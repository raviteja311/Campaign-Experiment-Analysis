# Campaign Experiment Analysis

A pre-registered analysis of a real randomised email campaign: did it work,
for whom, and is it worth rolling out? The repository goes from a written
test plan to a one-page decision memo, with every number regenerated by one
command and checked by tests.

**Result:** both emails raised revenue per customer. The pre-registered rule
recommends the **Mens email**: **+$0.77 per customer** (95% CI +$0.50 to
+$1.06), about **+$0.26 net profit per email** at the assumed margin, and it
out-earns the Womens email by $0.35 (p 0.03). Read the
[decision memo](reports/DECISION_MEMO.md) or the
[full report](reports/REPORT.md).

## Overview

The Hillstrom MineThatData dataset records a real experiment: 64,000
customers who bought from a retailer in the previous year were randomly
assigned to receive a Mens email, a Womens email, or no email, and their
visits, purchases and spend over the next two weeks were recorded.

This project analyses it the way a product analytics team would analyse a
live A/B test: the plan is fixed first, validity is checked before any
effect is read, effects carry honest uncertainty, multiple comparisons are
corrected, and the output is a business decision with its assumptions
stated.

## Problem statement

A marketing team needs three answers before sending an email to the whole
customer base:

1. Does either email increase revenue per customer?
2. Is the increase worth the cost of sending it?
3. Which email, and does it harm any customer group?

A naive comparison of averages answers none of these reliably. It ignores
whether randomisation worked, how noisy revenue is, how many comparisons
were run, and what the email costs.

## Objectives

- Pre-register metrics, tests, thresholds and a decision rule before
  analysing outcomes ([docs/TEST_PLAN.md](docs/TEST_PLAN.md)).
- Define metrics once, in SQL.
- Check the experiment's validity before reading any effect.
- Estimate effects with confidence intervals that do not depend on a single
  approximation.
- Turn the estimate into a profit decision whose assumptions are explicit.
- Make every reported number reproducible and tested.

## Architecture

```
params.yaml ──> config.py (typed, validated)
                     │
                     v
  minethatdata.com ──> data.py: download, SHA-256 verify, validate ──> pandas DataFrame
  (HTTPS mirror as fallback)                                               │
                                                                           v
                                            metrics_sql.py: DuckDB + sql/*.sql
                                                                           │
                                                                           v
  analysis.py, in the order of the plan:
    checks (SRM, balance) -> stats (Welch, bootstrap, Holm) -> robustness
    -> secondary metrics -> head to head -> variance_reduction -> power
    -> segments -> economics -> decision -> peeking -> uplift
                                                                           │
                                                                           v
  report.py + figures.py ──> reports/results.json, REPORT.md, DECISION_MEMO.md, figures/
```

It is a batch analysis pipeline driven by a CLI. There is no API or
database server, because nothing needs to be served: the deliverable is a
decision and the evidence for it.

## Data source

**Kevin Hillstrom, MineThatData E-Mail Analytics and Data Mining Challenge
(2008).** 64,000 rows, 12 columns:

| Column | Meaning | Timing |
|---|---|---|
| `recency` | Months since last purchase | Pre-period |
| `history`, `history_segment` | Dollars spent in the past year, and its band | Pre-period |
| `mens`, `womens` | Bought mens / womens merchandise in the past year | Pre-period |
| `zip_code` | Rural, Surburban (sic), Urban | Pre-period |
| `newbie` | New customer in the past 12 months | Pre-period |
| `channel` | Phone, Web, Multichannel | Pre-period |
| `segment` | Assigned arm | Treatment |
| `visit`, `conversion`, `spend` | Outcomes in the two weeks after the send | Outcome |

## Data-loading approach

The file is 4 MB (0.4 MB gzipped on the mirror), so it is not streamed. It
is downloaded once into `data/raw/`, which is git-ignored, and reused on
every later run.

1. If a cached copy exists and its SHA-256 matches the digest pinned in
   `params.yaml`, it is used with no network call.
2. Otherwise the canonical file is downloaded from minethatdata.com, with up
   to three attempts and exponential backoff, into a temporary file that is
   renamed only on success.
3. The canonical source is plain HTTP, so integrity rests on the pinned
   digest. A mismatch deletes the file and falls back to an HTTPS mirror
   with its own pinned digest.
4. The data is then validated (schema, domains, and consistency rules such
   as "a purchase always has a visit") before any analysis runs.

No data is committed. Another developer gets byte-identical input by
running any command; the checksum guarantees it.

## Configuration

All settings live in `params.yaml` and are loaded into typed, frozen
dataclasses. Unknown or missing keys and invalid values fail at load time.

| Section | Controls |
|---|---|
| `data` | Source URLs, pinned SHA-256 digests, cache directory, timeout, retries |
| `experiment` | Arms, allocation, metrics, alpha, power, SRM and balance thresholds, CUPED covariate, segments, winsorisation quantile |
| `bootstrap` | Resamples, confidence, seed |
| `economics` | Assumed gross margin, cost per email, rollout size |
| `peeking` | Simulation size and number of looks |
| `uplift` | Arm, outcome, split, seed, bins |
| `posthoc` | The post-hoc sensitivity cap (labelled as not pre-registered) |

No secrets, API keys or environment variables are needed.

## Usage

```bash
campaign-experiment download   # fetch and verify the data (optional; run does it)
campaign-experiment plan       # planning MDE grid; uses no outcome data
campaign-experiment run        # full analysis -> reports/
```

`python -m campaign_experiment run` is equivalent. A full run takes about
seven seconds on a laptop.

## Methods

- **Primary metric:** revenue per customer, including zeros, so the
  comparison stays randomised. Average order value is reported but never
  tested, because it conditions on a post-treatment outcome.
- **Tests:** Welch's t-test from SQL-computed sufficient statistics, with a
  percentile bootstrap (2,000 resamples) as an approximation-free check;
  two-proportion z-tests for rates; Holm correction within each family.
- **Validity:** chi-square sample-ratio test; standardised mean differences
  for every pre-period covariate.
- **Variance reduction:** CUPED on last year's spend, and a Lin (2013)
  interacted regression with HC2 robust errors.
- **Decision rule:** an email qualifies only if validity passes, its
  Holm-adjusted lift is positive and significant, the capped-spend check
  agrees, no segment shows significant harm, and expected net profit is
  positive. Among qualifying emails, the most profitable wins.

Full detail: [PROJECT_DOCUMENTATION.md](PROJECT_DOCUMENTATION.md).

## Results

| | No email | Mens email | Womens email |
|---|---|---|---|
| Revenue per customer | $0.65 | $1.42 | $1.08 |
| Lift (95% bootstrap CI) | | +$0.77 (+$0.50 to +$1.06) | +$0.42 (+$0.17 to +$0.68) |
| Conversion rate | 0.57% | 1.25% | 0.88% |
| Visit rate | 10.62% | 18.28% | 15.14% |
| Net profit per email (assumed 40% margin, $0.05 cost) | | +$0.26 | +$0.12 |
| Break-even gross margin | | 6.5% | 11.8% |

- **Validity:** SRM p 0.904; largest covariate |SMD| 0.014 (threshold 0.1).
- **Head to head:** Mens beats Womens by $0.35 per customer (95% CI +$0.03
  to +$0.66, p 0.03).
- **Segments:** the Mens email lifts revenue significantly in all 11 segment
  levels after Holm correction; the Womens email in 3 of 11 (new customers,
  womens-only buyers, urban customers).
- **CUPED removed only 0.04% of variance.** Last year's spend has a
  correlation of 0.02 with two-week spend, so it is a poor covariate here.
  This is reported as a finding, not hidden.
- **Peeking:** checking an A/A test 20 times and stopping at the first
  p < 0.05 produced 23.1% false positives instead of 5%.
- **Uplift model (exploratory):** targeting the top 30% of customers by
  predicted uplift captures 55% of the Womens email's incremental visits
  (normalised Qini 0.23, held-out data).

Two honest caveats: the source file top-codes spend at $499, which makes
the pre-registered 99th-percentile cap non-binding (a labelled post-hoc
95th-percentile check gives +$0.74 and +$0.41); and margin and email cost
are assumptions, which is why break-even margins are reported.

## Testing

```bash
pytest              # 97 offline tests on synthetic data with known effects
pytest -m network   # 2 tests on the real data, including a byte-for-byte check
                    # that the committed reports match a fresh run
ruff format --check . && ruff check .
```

The statistics are tested against references (scipy, statsmodels) and
against synthetic experiments whose true effect is known, including an A/A
check that the false-positive rate is nominal and a check that CUPED is
unbiased under the null.

## Limitations

- **Revenue, not profit:** margin and cost per email are assumptions.
- **Two-week window:** no data on later purchases, unsubscribes or fatigue,
  so those guardrails could not be checked.
- **Top-coded spend** at $499 understates large orders in every arm.
- **Segment and uplift findings are exploratory** and need their own
  randomised test before anyone acts on them.
- **Public dataset:** its results have been known since 2008. The plan fixes
  the method before analysis in this repository; it cannot make the author
  unaware of the literature (see the note in the plan).
- **Retail, not banking:** the methods transfer directly; the numbers do not.

## Future improvements

- A pre-period covariate measured over a matching two-week window, so CUPED
  has something to work with.
- Group-sequential boundaries (O'Brien-Fleming) instead of the Bonferroni
  illustration, to allow safe early stopping.
- A targeted-versus-send-to-all experiment to validate the uplift model.
- Calibration checks on the uplift model's two classifiers.
